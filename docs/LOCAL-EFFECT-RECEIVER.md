# Trusted local filesystem effect receiver: scope and failure semantics

`trusted_stack.outbox_receiver.deliver_record` publishes **one real filesystem object** for a previously reviewed and committed `effect_records` row. This is a narrow step beyond SQLite-only effect recording, **not** a mechanism for intercepting arbitrary actions or a deployment safety guarantee.

The trusted process must be the actual OS UID owning the controller SQLite database and must be a configured `admins` principal. It uses a caller-provisioned, private, trusted-UID-owned receiver directory (no group/other permissions), opened with `O_DIRECTORY|O_NOFOLLOW`. The destination string approved by the reviewer is only **metadata**; it never becomes a filesystem path. The only writable effect is a fixed `<release_id>.body` file under that receiver. The interface is **not** exposed to untrusted agents through the Unix-socket broker.

The committed SQLite effect record is validated against its release row and SHA-256 body before publication. Delivery takes SQLite `BEGIN IMMEDIATE`, the same serialization lock as HALT. Files are written to a random private temporary name, fsynced, atomically linked with no overwrite, and the directory fsynced; only then is an SQLite delivery receipt committed. Repeated delivery verifies exact existing content rather than republishing. If the delivery process crashes after durable publication but before receipt commit, a retry checks the existing file and commits a receipt. The interrupted post-link/pre-unlink crash state (two links to the exact reviewed inode, one matching private random temporary name) is also reconciled by deleting only that temporary link and fsyncing before committing the receipt. An unrelated extra hardlink, ambiguous temporary name, different existing bytes, symlink, absent received file after a committed receipt, bad owner/mode, failed write or inconsistent digest fails closed.

**Important limitation:** the filesystem operation and SQLite receipt are not a single cross-resource atomic transaction. If the delivery process dies after publication and HALT commits before recovery, the file legitimately exists without a delivery receipt: it was published before HALT's SQLite lock acquisition. HALT cannot undo such in-flight or completed external effects. Host admin, filesystem power-loss ordering, SQLite durability, complete mediation of agents' other capabilities, OS clock, isolation of trusted owner and output root are assumptions, not proofs. This is only an idempotent exact-byte receiver, not universal sandboxing, credential escrow, network quarantine, bank dispatch, or trusted remote receipt.

Tests: `python3 -m unittest trusted_stack.test_outbox_receiver -v` and the full `trusted_stack` suite. Crash fault injection is direct trusted Python test access only; do not enable it in public RPC paths.

Delayed delivery additionally rechecks used approval identity, lease revocation, lease expiration and approval expiration **before** local file publication, under the SQLite lock with one trusted timestamp sample. A previously authorized database effect record is not an unlimited durable external-dispatch capability. Expiration during an in-progress file publication is interpreted relative to the trusted clock sample at the beginning of the serialized operation; the operation cannot retroactively undo bytes already published.

For a real separate trusted process, a one-shot CLI entry point is provided: `python3 -m trusted_stack.deliver_cli --db /private/gate.db --out /private/effects --release-id 1 --agents UID1 --reviewers UID2 --approvers UID3 --admins TRUSTED_UID`. The CLI derives the actual UID from the OS; supplied role IDs cannot bypass SQLite database owner and private directory ownership checks. It **cannot** be called as an agent RPC and does not bootstrap, migrate or create privileged destination directories. Never share database or receiver ownership with an untrusted agent.
