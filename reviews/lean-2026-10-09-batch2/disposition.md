# Disposition: Gemini 3.1 Pro review of Authenticated, SC26Authenticated, SC26Refinement, SC23Isolation and Cert

| File | Finding | Disposition |
|---|---|---|
| Core/Authenticated | `trusted_claim_not_adversary` is a tautology. Nothing constrains the trace with respect to U. | **Agreed; it was a labelling problem.** The content is `authed_run` and `claim_issued_by`: an operation claiming identity x takes effect only if issuer = x, so forging the claim field is useless. Issuer authenticity (platform identity, e.g. SO_PEERCRED, is the true issuer) remains the single explicit premise, and the theorem does not prove it. A formally constrained adversary generator is being added (`Core/AuthenticatedAdv.lean`, in progress). |
| SC26Authenticated | "Cannot manufacture consent" follows from the disjointness of U and the approvers. A stolen approver key is not excluded. | **Agreed on scope.** Key theft violates the issuer-authenticity premise. The theorem shows that forging the claim is useless, not that credentials can't be stolen. The wording now states this. |
| SC26Refinement | `bankCall` from non-gate callers is a no-op, so attacks are "neutralised by bug". | **Misread.** Dropping direct calls from non-gate callers IS the bank's authentication (`bankAuth`, the receiver accepts only the gate's credential). `legal` excludes untrusted operations carrying the gate credential, and `no_bank_auth_breaks` in the model shows what happens without this check. No change. |
| SC23Isolation | The planner is blind: `plan` ignores `pvals`. | **Valid.** In progress: `SC23IsolationV2` lets the planner read its own trusted values and handle ids, and keeps noninterference. |
| SC23Isolation | `confirm` is not authenticated; a forged user confirmation passes. | **Valid; this is the credential-separation premise.** In progress: V2 wraps `confirm` with `Core/Authenticated`. |
| Core/Cert | `min` carries both premise lists. | **Valid, minor.** In progress: `best` keeps only the chosen certificate's premises. `min` remains sound, but it requires both premise sets. |
| Cross-cutting | "Defining away the adversary." | **Partly fair.** Trust-boundary premises (issuer authenticity, receiver authentication, planner isolation) are premises. Each is now named in the typed ledger (`ASSURANCE-LEDGER.md`), with a necessity witness showing that dropping it breaks the result. The models do not prove these premises; the runtime tests exercise them on one host. |
