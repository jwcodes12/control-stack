### File 1: ControlStack/Core/Authenticated.lean
**Verdict:** The file introduces an authentication wrapper but fails to link it to any formal model of an adversary or threat capability. The core security claim relies entirely on reading English semantics into unconstrained variables and list membership.

**Defects:**
1. **Location:** `trusted_claim_not_adversary`. 
   **Problem:** Definitional tautology presented as a security result. The theorem purports to prove that the adversary "did not issue" an operation simply by showing `io.1 ∉ U`. Because the trace `ops` is universally quantified as an arbitrary list with no relationship to `U` or any adversary trace generator, the conclusion immediately and trivially follows from the explicit premise `hx : x ∉ U` and the equality `io.1 = x`. 
   **Instance:** Any trace `ops` whatsoever, whether generated honestly or manually typed by an attacker who magically controls all identities, trivially satisfies this implication because `U` is just an arbitrary parameter passed to the lemma. 
   **Fix:** Formally define an adversary step relation that is physically restricted to identities in `U`, or add a trace well-formedness premise (e.g., `∀ io ∈ ops, io.1 ∈ U ∨ IsHonest io`) to anchor the adversary's capabilities.

**Overclaims:** The docstring claims "if `x ∉ U`, the adversary did not issue it", overstating the formal result. The theorem proves nothing about an adversary's actions; it merely proves list non-membership.

### File 2: ControlStack/Scenarios/SC26Authenticated.lean
**Verdict:** This scenario inherits the vacuity from `Core/Authenticated` regarding the adversary's capabilities. It relies on a definitional tautology to claim that an adversary cannot forge approvals, proving only trivial disjointness.

**Defects:**
1. **Location:** `sc26_safe_authenticated`. 
   **Problem:** The theorem claims to prove that "the adversary cannot manufacture consent" by showing that an approval is issued by an approver `a` such that `a ∉ U`. However, this is a direct definitional tautology: since the theorem takes `hU : ∀ u ∈ U, u ∉ R.approvers` as a premise, the conclusion `a ∉ U` instantaneously follows from `a ∈ R.approvers`. 
   **Instance:** An adversary who steals an approver's key and generates a trace `ops` containing that approver's ID will still perfectly satisfy `a ∉ U`, simply because `U` is defined to exclude approvers. 
   **Fix:** Restrict the trace `ops` to be generated by a transition system where the adversary can only inject operations using identities within `U`, forcing the proof to rely on the unforgeability of approver operations rather than set disjointness.

**Overclaims:** Claims "the adversary cannot manufacture consent", but the theorem provides no such guarantee since the adversary isn't formally constrained from producing operations under approver identities.

### File 3: ControlStack/Scenarios/SC26Refinement.lean
**Verdict:** The concrete machine simulation contains a fatal logic error in how direct bank calls are handled. This error makes adversarial interference impossible by simply dropping valid cross-principal calls, rendering the simulation's coverage of network behavior vacuous.

**Defects:**
1. **Location:** `stepC` for `bankCall` and `legalC`. 
   **Problem:** `stepC` incorrectly processes bank calls *only* if `c = R.gate` (via `if c ≠ R.gate then s else { s with bank := ... }`). However, `legalC` explicitly requires `c ≠ R.gate` for all valid traces. Consequently, *every* legal bank call evaluates the true branch and returns `s` (a no-op), completely dropping direct bank calls by other principals. 
   **Instance:** An adversary injects `.bankCall 99 1 tx` (where 99 is an untrusted principal). This is legal under `legalC` (since 99 ≠ gate), but `stepC` simply returns `s`, leaving the bank unchanged and neutralizing the attack by bug rather than design. 
   **Fix:** Correct the conditional in `stepC` to `if c = R.gate then s else { s with bank := ... }` so non-gate principals can legitimately interact with the bank state.

**Overclaims:** Claims the refinement covers "arbitrary interleaving... and network behaviour" including "direct calls to the bank by other principals", but the model completely nullifies these external calls.

### File 4: ControlStack/Scenarios/SC23Isolation.lean
**Verdict:** The formalization of "structural planner isolation" achieves safety by completely lobotomizing the planner's ability to read its own history. Furthermore, it assumes but does not formalize the authentication of user confirmations, leaving a major vulnerability to trace forgery.

**Defects:**
1. **Location:** `step` for `derive` and `w1_impossible`. 
   **Problem:** The planner derivation step computes `E.plan s.user s.pvals.length`, completely ignoring the actual contents of `s.pvals`. The planner has zero read access to its own trusted derivations or the ordering of events. `w1_impossible` succeeds not because of isolation, but because the planner is a blind function of the step counter. 
   **Instance:** Even if `s.pvals` contains purely trusted honest inputs, `derive` cannot read them to make decisions, making the planner functionally useless and structurally blind to *all* tool outputs. 
   **Fix:** Expose a sanitized or masked version of `s.pvals` to `E.plan` so the planner can legitimately compute over its history.
2. **Location:** `step` for `confirm` and `sc23_isolated_safe`. 
   **Problem:** The trace `ops` is universally quantified, meaning an adversary can freely inject operations. The `.confirm` step accepts input as long as `c ∈ E.users`, but lacks any formal authentication guard to ensure the user actually issued it. 
   **Instance:** The adversary freely injects `[.toolResult 66, .confirm 1 0 5 [66], .act 5 [0] 0]` into `ops`. The system accepts the forged confirmation from "user 1" and executes the tainted action, breaking the intended security while still passing the tautological `sc23_isolated_safe` theorem. 
   **Fix:** Add a formal authentication guard for `.confirm` (similar to `Authenticated.lean`) to prove that only genuine users can issue confirmation events.

**Overclaims:** Claims "injected content cannot influence any trusted value" and "structural planner isolation," but achieves this solely by entirely eliminating the planner's ability to read its own trusted state.

### File 5: ControlStack/Core/Cert.lean
**Verdict:** The certificate calculus systematically inflates the assumption ledger by using a logically flawed `min` operator. This weakens the resulting composed certificates by formally requiring unnecessary premises to hold.

**Defects:**
1. **Location:** `ProbCert.min` and `QtyCert.min`. 
   **Problem:** When combining two certificates bounding the same quantity, the `min` operator unconditionally concatenates the premises of both (`c₁.premises ++ c₂.premises`). Logically, the bound `Min.min c₁.bound c₂.bound` only requires the premises of the certificate that actively provides the minimum bound. 
   **Instance:** If `c1` proves a bound of 0 under premise A, and `c2` proves a bound of 1 under premise B, `QtyCert.min c1 c2` correctly yields a bound of 0 but artificially demands that *both* A and B hold, making the certificate strictly harder to satisfy than `c1` alone. 
   **Fix:** Define `min` to select the certificate with the smaller bound conditionally (e.g., `if c₁.bound ≤ c₂.bound then c₁ else c₂`), propagating only its specific required premises into the ledger.

**Overclaims:** Claims the resulting list is the "complete assumption ledger of the composed bound," implying necessity, but the `min` operations permanently bake in superfluous premises that are mathematically disjoint from the achieved bound.

### Cross-cutting
**Verdict:** Across the ControlStack repository, security properties are systematically "proven" by defining away the adversary. Whether through unconstrained trace quantifiers (where arbitrary list membership masquerades as origin authentication), backwards conditionals that silently drop adversarial actions, or structurally lobotomized components that ignore all inputs, the formal guarantees rest heavily on definitional tautologies and implementation bugs rather than robust system constraints or actual threat mitigation.
